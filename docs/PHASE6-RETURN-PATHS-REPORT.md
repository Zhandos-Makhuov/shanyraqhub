## 1. Executive summary
Участник, нажавший на push или на кнопку под сообщением бота, попадал на главную. Нужную встречу или тему приходилось искать самому. Системная кнопка «Назад» (Android, Telegram) сразу закрывала сайт, а перезагрузка сбрасывала на главную. Записи на встречу у организатора не обновлялись без перезагрузки. Открытое уведомление не отмечалось прочитанным: работала только кнопка «прочитать все».

Сделано одним потоком:
1. **Прямые ссылки:** `/?event=<id>`, `/?topic=<id>`, `/?n=<id уведомления>`. Push и бот ведут на `?n=…`: сайт открывает встречу, тему или раздел и отмечает уведомление прочитанным. Ссылка переживает экран входа. Недоступная цель — честное сообщение. В окне встречи появилась кнопка «Сілтеме».
2. **«Назад» во всём приложении.** Разделы и окна стали записями истории браузера. «Назад» закрывает окно, потом возвращает в прежний раздел, на первой записи выходит с сайта. В Telegram появляется его кнопка «Назад». После перезагрузки раздел сохраняется.
3. **Вживую:** правки встреч, записи и отмены — через Realtime. Посещения сознательно не включены: удаление посещения раскрыло бы, кто пришёл.
4. **Уведомления:** открытое уведомление отмечается прочитанным по одному (колокольчик, push, Telegram). «Новый отзыв» открывает вкладку «Пікірлер». Нажатие на push при открытом сайте открывает само уведомление.

## 8. Устройство прямых ссылок
- Формат — query string: Telegram дописывает свои данные в hash и не мешает ей. Одна ссылка — одна цель; при нескольких параметрах берётся первый по порядку `n`, `event`, `topic`.
- Ссылка только выбирает, **что открыть**. Сами данные загружаются как обычно, под RLS. Встреча, которую участник не видит, получает сообщение «қолжетімсіз». Чужое уведомление не находится и не отмечается прочитанным (проверено на тестовой базе).
- Без входа ссылка ждёт в `sessionStorage` и открывается после входа (паролем или через Telegram). Ограничение: после перехода по письму подтверждения почты ссылка теряется (P6-15).
- Схема расширяется на другие цели (`?book=` и т. п.) без перестройки. Сейчас не добавлялось: нет потребности.

## 13. RLS и безопасность
- Права не расширялись. Realtime для INSERT/UPDATE соблюдает RLS. `event_attendance` не опубликована: DELETE раскрыл бы «кто пришёл» — это защищено серверной проверкой «C-23: event_attendance NOT in the publication».
- `?n=` раскрывает только своё (RLS). Чужой id — «қолжетімсіз», без изменений (live D1/D2).
- Ссылка не обходит вход и права: она лишь выставляет намерение «открыть».
- Функция бота: без секрета `?dispatch` → 403 (подставной API и тестовый проект).
- Формат id проверяется; некорректная ссылка игнорируется (e2e `<script>`).

## 24. Дополнение: C-23a — решение владельца «да» (25.11.2026)
- **Проблема:** RLS (C-21) скрывает чужие отменённые записи, поэтому Realtime не присылал отмену обычным участникам. Вариант «тронуть строку встречи» отклонён: `events_audit` писал бы строку журнала аудита на каждую запись (засорение журнала).
- **Решение:** миграция `20261125000002_c23a_registration_broadcast.sql`. Триггер `registrations_broadcast` срабатывает после смены статуса или удаления записи и вызывает `realtime.send` в **закрытый** канал `shq-events`. В сообщении только `{event_id}`, без людей и посещений. Ошибка отправки не мешает записи или отмене. Политика `shq_events_broadcast_read` на `realtime.messages` разрешает чтение только `authenticated`. Сайт (`subscribeLive`) слушает канал и перезагружает данные как обычно, под RLS.
- **Проверки:**
  - серверные — 274/274 (+3: подсказка отправляется при отмене, политика только для вошедших, триггер есть);
  - live на тестовой базе — 16/16 (B3 «отмена чужой записи у участника вживую» теперь PASS; стойка организатора 2/2);
  - гость не может подписаться на канал: `CHANNEL_ERROR: Unauthorized`, 0 сообщений;
  - e2e — 236/236.
- **Попутно (P6-17):** нестабильные проверки `forum-manage` (2 сбоя из 5 полных прогонов) и `forum.spec` «Tab + Enter / Space» (1 сбой) — гонки внутри тестов: сайт переводит фокус в следующем кадре. Добавлено ожидание фокуса; после этого 3 полных прогона подряд — 236/236.
- Боевая база: как и остальные миграции Phase 3–6 — только со слиянием и по отдельному «да».
