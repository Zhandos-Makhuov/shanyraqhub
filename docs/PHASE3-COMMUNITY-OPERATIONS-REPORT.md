# Phase 3 — Community System & Operations. Отчёт

Дата: 23.11.2026. Ветка `claude/sleepy-brown-4zolp6`. В `main` не вливалось, деплоя не было, production и боевая база не изменялись. Миграции, RLS, RPC, Edge Functions, награды, роли, auth и Telegram не менялись.

## 1. Кратко
Платформа уже умела почти всё нужное для управления сообществом: правила базы разрешают организатору менять и отменять свою встречу, сервер защищает отметки и записи от дублей. Но интерфейс этим не пользовался, а для повседневных операций был неудобен. Что сделано:

1. **Организатор управляет своей встречей.** В окне встречи для её организатора и модератора+ появился блок «Ұйымдастырушыға». В нём:
   - список записавшихся (пришедшие отмечены);
   - «Өзгерту»;
   - «Кездесуді тоқтату» с подтверждением, где указано число записавшихся;
   - «Кездесуді қайтару».

   Отменённая встреча видна с меткой, записаться на неё нельзя, на главной она не предлагается.
2. **Стойка отметки на входе.** Было: два длинных списка — все встречи (первой шла самая старая) и все участники клуба — плюс искусственная задержка 0,8 с. Стало:
   - в списке только встречи, где этот человек вправе отмечать;
   - у каждого записавшегося — кнопка «Белгілеу» и счётчик «тіркелгендер · келгендер»;
   - пришедших без записи можно найти по имени;
   - себя отметить нельзя (кроме супер-админа);
   - если подходящих встреч нет, это объясняется.
3. **Запись, отмена, отзыв, создание встречи.** Пока сервер отвечает, на кнопке «Күте тұрыңыз…», повторное нажатие игнорируется. Ошибка видна рядом, а не во всплывающем окне браузера. Форма не закрывается и не теряет данные. После успеха — сообщение на странице. Окна встречи доступны с клавиатуры и для скринридера.
4. **Честность.** Кнопка обещала «Опубликовать и оповестить», но сервер о новых встречах не рассылает — теперь просто «Жариялау». По умолчанию предлагается завтрашняя дата, а не вписанная `2026-11-25`; прошедшую дату форма не принимает.
5. **Уведомление → встреча.** Уведомление о записи или напоминание открывает саму встречу. Если встреча удалена — объяснение.
6. **Рейтинг (список участников).**
   - Найденный поиском участник больше не становится «#1» — показывается его настоящее место.
   - «Книги» считают только прочитанные.
   - Строки рейтинга доступны с клавиатуры.
7. **Админка.**
   - Роль раньше менялась сразу при выборе в списке — теперь только после подтверждения «было → станет».
   - Подтверждение добавлено для начисления коинов и отзыва достижения.
   - Результаты действий — сообщениями на странице.
   - Уровни и роли показываются по-человечески, а не кодами.
   - Есть поиск по имени или @нику и фильтр по роли.

**Проверки:** lint ✅, сборки демо и боевая ✅, e2e **183/183** (+23 новых), axe 0 нарушений на 14 состояниях, **тестовая база 20/20**. Статус CI — в сообщении в чате.

## 4. Технические решения
1. **Без изменений backend.** Правка и отмена встречи — прямой update `events` под существующей политикой `events_update` (автор-организатор или модератор+). Запрос возвращает `.select('id')`: если изменено 0 строк, это показывается как отказ. Права в интерфейсе (`canManage`, `canManageEvent`) повторяют RLS.
2. **Отмена вместо удаления.** Удаление (admin+) каскадом стирает записи, посещения и отзывы, поэтому в интерфейс оно не выведено. Отмена обратима: «Кездесуді қайтару» работает до начала встречи.
3. **Что в правке не меняется.** Нельзя менять направление (от него зависят достижения «5 посещений»). Мест не может быть меньше, чем уже записалось. Перенос в прошлое запрещён. Если есть записавшиеся, организатор видит предупреждение, что сайт им не сообщит и напоминания могут прийти по старому времени (C-13).
4. **Стойка отметки по правилам сервера.** Показываются только встречи, где `manual_check_in` пройдёт: организатор этой встречи или модератор+, не отменена, с −2 ч. Сначала идущие и сегодняшние. Повторную отметку сервер всё равно не создаст (`record_attendance`), а интерфейс сразу показывает «Қатысты».
5. **Подтверждение для действий с правами.** Список выбора роли остаётся «управляемым»: пока нет подтверждения, он показывает прежнюю роль, а «Болдырмау» возвращает её на экране. Подтверждение — `alertdialog` из форума (`ConfirmDialog`).
6. **Ошибки на месте, без `alert`.** Функции контекста возвращают `{ ok, error }`; live вызывается в «тихом» режиме. Ошибки админских действий по-прежнему приходят прежним путём (`alert` при отказе сервера) — интерфейс этого блока не переписывался (C-22).
7. **Уведомление → встреча.** Используется готовое намерение `setEventsIntent` и событие окна (как у форума в 2.4.2). Встреча открывается только если уведомление ведёт в «События»: иначе «Қатысу расталды» оставлял бы висящий переход.

## 8. Требуют решения владельца
1. **C-5.** Рассылать ли участникам уведомление о новой встрече. Настройка `notify_new_events` есть, но не используется. Нужен триггер — миграция.

3. **C-14.** Нужна ли отмена ошибочной отметки: RPC модератор+ с причиной, списанием награды (без минуса) и аудитом — миграция.
4. **C-15.** Ограничивать ли ручную отметку по времени (сейчас можно отметить и через несколько дней).
5. **C-21.** Оставить ли списки записавшихся и посещения видимыми всем участникам через API (RLS) или закрыть их.
6. *(прежний)* Оценки 3–5 или 1–5 в отзыве об участнике.

## 10. Риски
- **Низкий:** после переноса встречи напоминания приходят по старому времени (C-13). Интерфейс предупреждает организатора.
- **Низкий:** ошибки админских действий по-прежнему показываются через `alert` (C-22, без изменений).
- Награды, права, данные: не менялись; все проверки прав выполняет сервер.

## 11. Физическая проверка (по желанию, 3 действия, Android, https://shanyraq-demo-auto.pages.dev после сборки; меню профиля → тестовый аккаунт «Дана Серік»)
1. «Тағы» → «Қатысу тарихы» → «Белгілеу» у участника в списке: кнопку удобно нажимать, появляется «Қатысты».

3. Записаться на будущую встречу, затем в колокольчике нажать уведомление о записи — открывается сама встреча.
