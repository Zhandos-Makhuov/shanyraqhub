## 2. C-21 — список записавшихся для всех участников

**Решение владельца (Phase 4):** все авторизованные участники могут видеть, кто записался на встречу.

- **База (тестовая):** политика `registrations_read` — участник видит активные записи (`status = 'registered'`) всех встреч; свои записи — в любом статусе; организатор встречи и модератор+ — все, включая отменённые. Отменённые записи других участников не видны. Прав на изменение нет (только `register_for_event` / `cancel_event_registration`). У гостя (`anon`) нет доступа к таблице. В таблице нет личных полей (только кто/какая встреча/статус/время); телефоны — в `profile_contacts` (только сам и admin).
- **Посещения не открывались:** `event_attendance` по-прежнему видят сам участник, организатор встречи и модератор+ (решение C-21 от 23.11 в этой части сохраняется); числа — через `get_event_counts` / `get_member_stats`.
- **Сайт:** в окне встречи у участника — блок «Кім тіркелді · N» (имена и аватары, до 24 имён + «тағы N»); без отметок «пришёл»; у организатора/модератора — прежний блок «Ұйымдастырушыға» (без дублирования). У отменённой встречи список не показывается.
- **Проверки:** серверные (`security_tests.sql`): участник видит 2 активные записи, чужую отменённую — нет; `update`/`delete`/`insert` чужих записей — `permission denied`; гостю — `permission denied`. API (`supabase/tests/api-access.py`, 31/31). Сайт на тестовой базе (8/8): участник видит обоих записавшихся, не видит отменившего, нет инструментов организатора; организатор видит «2 / 10» в своём блоке. e2e: `community-ops.spec.ts` — «every member sees who signed up».

## 3. Безопасность (RLS / RPC / Edge Functions)

### 3.1 Прямая проверка API (тестовая база, `supabase/tests/api-access.py`, 31/31)
Гость: `event_registrations`, `event_attendance`, `profiles`, `profile_contacts`, `reward_ledger`, `get_member_stats` → 401.
Участник (`claude-test`): записывается через RPC; видит записавшихся (C-21); чужие посещения, телефоны, история коинов, уведомления, настройки — пусто; изменить/удалить/создать чужую запись → 403; изменить свой баланс / журнал наград / свою роль → 403; `manual_check_in`, `undo_check_in`, `admin_adjust_coins`, `set_user_role`, `award_achievement` → `forbidden`; изменить чужую встречу → 0 строк; `get_member_stats` отдаёт только `user_id` + число.
Организатор встречи: видит все записи своей встречи (3, включая отменённую), но не может менять их напрямую (403); `created_by` встречи ставит база (клиент не может подставить автора).

### 3.2 Советник Supabase (тестовая база, после миграции)
- `authenticated_security_definer_function_executable` (32, WARN) — **так задумано**: RPC вызываются вошедшими участниками, права проверяются внутри; гость их вызвать не может.
- `rls_enabled_no_policy` (2, INFO) — `event_checkin_tokens`, `scheduled_notifications`: доступ только через RPC/сервер — так задумано.
- `extension_in_public` (`pg_net`, WARN) — **DEFERRED**: расширение установлено Supabase; перенос в другую схему затрагивает cron-задачи push/Telegram — отдельно и осторожно.
- `auth_leaked_password_protection` (WARN) — **NEEDS OWNER DECISION**: включается владельцем в панели Supabase (Auth → Passwords; может требовать платный план).

### 3.3 Edge Functions
Не менялись. Проверено ранее (этап 7/8, Telegram): `send-push` без секрета — 403, webhook бота без секрета — 403, поддельный `initData` — 401.

## 4. Целостность данных

- **S-3** (удаление прочитанной книги через API освобождает недельный зачёт) — подтверждено анализом, **не исправлялось** (логика наград — только с согласия): **NEEDS OWNER DECISION**. Рекомендация: в RLS разрешить удаление только `status = 'reading'` (интерфейс и так удаляет только «Читаю») — одна строка миграции, на начисления не влияет.
- **Проверено, проблемы нет:** метрика `books_reviewed` (все прочитанные с рецензией ≥100, без недельного лимита) используется только достижением с порогом **1** («первая рецензия»); книжные достижения 1/5/10/25 считают `books_completed` (с недельным лимитом). Изменение рецензии после зачёта награду не меняет.
- **P4-10 (Low, OPEN — backend):** организатор через API может уменьшить число мест ниже числа записавшихся (проверка только 1–10000). Интерфейс не позволяет; новые записи после этого сервер не принимает — данные не портятся. Возможная защита — проверка в триггере (миграция).
- Индексы на внешние ключи ускоряют проверки прав (`events.created_by` в политиках записей/посещений) и каскадное удаление участника.
