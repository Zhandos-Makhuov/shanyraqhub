## 2. S-3 — удаление прочитанных книг

**Решение владельца (24.11.2026): вариант «только RLS».**

- **Было:** RLS `user_books_delete_own` разрешал владельцу удалить любую свою запись. Удаление засчитанной книги освобождало недельный зачёт: правило «одна книга в неделю» смотрит на оставшиеся записи.
- **Стало (миграция):** владелец удаляет только записи со статусом `reading`; модератор+ — любые, как раньше (модерация). Логика начислений не тронута.
- **Проверено:**
  - SQL: участник удаляет «Читаю» — да; удалить «Прочитана» — запись остаётся; модератор удаляет — да.
  - API: удаление «Читаю» — 200 и 1 строка; удаление «Прочитана» — 200 и 0 строк, запись на месте; прямая смена `status` — 403, менять статус можно только через `save_user_book`.
  - Интерфейс: «Убрать с полки» и раньше показывалось только для «Читаю» (e2e `books-knowledge.spec.ts`).
  - Повторно получить зачёт через «удалить и создать заново» больше нельзя: запись не удаляется, а повторное сохранение той же книги идёт через `on conflict`, ключ награды уникален.
- **S-3a — остаток, DEFERRED (решение владельца 24.11.2026):** прочитанную книгу можно вернуть в «Читаю» (окно «Өзгерту» и `save_user_book`). Тогда недельная проверка её больше не видит, и в ту же неделю засчитывается ещё одна книга. Проверено на тестовой базе в транзакции с откатом: зачётов стало 2 за одну неделю. Закрыть можно двумя способами: (а) запретить переход «Прочитана → Читаю»; (б) считать неделю по журналу наград. Оба — отдельное решение (логика или бизнес-правило).

## 6. P4-10 — места не меньше записавшихся
- **Миграция:** триггер `events_capacity_guard` (`before update of capacity`): при уменьшении мест считает активные записи и отказывает с ошибкой `capacity_below_registered`. Записи не отменяются и не удаляются. Сайт показывает ошибку по-казахски/по-русски/по-английски (ключ `evErrCapacityBelow` уже был).
- **Одновременные действия:** `register_for_event` блокирует строку встречи (`for update`), обновление мест тоже её блокирует, поэтому действия идут строго по очереди. Проверено двумя параллельными соединениями к тестовой базе в обоих порядках: в каждом случае выигрывает ровно одно действие, записавшихся никогда не больше мест.
- **SQL:** меньше — отказ; равно — можно; больше — можно; участник не может менять; записи целы.
- **API:** организатор ставит меньше — 400 `capacity_below_registered`; равно и больше — 200; участник — 0 строк; гость — 401; записи целы.
- **Сайт на тестовой базе (7/7):** организатор со «старым» экраном (записи не обновляются вживую, C-23) ставит 5 мест при 4 записавшихся — сохраняется; та же сессия ставит 3 — база отказывает, остаётся 5; JS-ошибок и системных окон нет.
- **Не проверено в браузере:** отказ сервера через форму. Форма требует минимум 5 мест, а в тестовой базе только 4 участника, кроме организатора; новых пользователей не создавал. Отказ проверен в SQL и API, сопоставление ошибки с текстом — в коде (`SERVER_ERRORS`).

## 7. P4-13 — `vendor` боевой сборки

**Состав (source map, минифицированные байты):** `react-dom` 202,1 кБ · Supabase ≈ 207 кБ (`auth-js` 97,6, `realtime-js` 31,0, `phoenix` 25,1, `storage-js` 22,7, `postgrest-js` 16,4, `supabase-js` 11,5, `iceberg-js` 5,2, `functions-js` 3,1) · `lucide-react` 20,4 · `canvas-confetti` 10,3 · `react` 8,0 · `scheduler` 3,4.

**Что нужно на старте боевого сайта:** React, Supabase (вход, загрузка данных, Realtime), значки. Storage нужен только для загрузки фото, но клиент Supabase подключает его сразу — отделить можно только переделкой клиента (не делалось). Confetti нужен только для анимации награды.

**Замеры** (боевая сборка, медленный 4G 1,6 Мбит/с + 150 мс, пустой кэш, медиана из 3):

| Вариант | `vendor` | Экран «Жүктелуде…» | Форма входа |
|---|---|---|---|
| До | 468,95 кБ (gzip 136,16) | 1607 мс, JS 228 кБ | 1918 мс, JS 242 кБ |
| Supabase отдельным файлом (опробовано) | 240,40 кБ + supabase 217,55 кБ | **1313 мс**, JS 170 кБ | **2120 мс (хуже на 0,2 с)**, JS 239 кБ |
| **Итог: confetti по требованию** | **458,36 кБ (gzip 132,32)** + confetti 10,58 кБ отдельно | 1597 мс, JS 224 кБ | 1908 мс, JS 238 кБ |

**Решение:** отдельный файл Supabase показывает «Жүктелуде…» на 0,3 с раньше, но форму входа (и данные) — на 0,2 с позже. Supabase тогда начинает качаться только после основного файла, а не параллельно с ним. Для участника важнее форма и данные, поэтому вариант отклонён (комментарий в `vite.config.ts`). Оставлено: confetti — по требованию (`src/utils/confetti.ts`; ошибка загрузки = просто без анимации). Эффект небольшой (−10,6 кБ, −4 кБ gzip, время в пределах погрешности). **Остаток P4-13 — DEFERRED с обоснованием:** дальнейшее уменьшение возможно только переделкой клиента Supabase (отложенный Storage/Realtime) или заменой React — это за рамками точечной правки.
